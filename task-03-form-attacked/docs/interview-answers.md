# CarePoint Clinic – Task 3 Interview Answers

### 1. Why did you use one `/auth` route for sign-up, login and password reset?

I used one `/auth` route for sign-up, login and password reset, with a different mode for each activity. This kept the three related activities together instead of creating separate pages. The trade-off is that the correct form must appear based on the selected mode. I tested the different URLs and checked that the right form appeared. I also checked the development server log, which showed that switching between forms did not make another server request. However, I noticed that when I switch from one form to another, anything I have already typed is lost. I accepted this trade-off for the assignment rather than keeping the information in memory. Claude helped build the route and its form behaviour.

### 2. Why is email format checked differently on sign-up and login?

On sign-up, the email format is checked as the patient types so they can correct mistakes early. On login, I chose to check the email format only when the patient submits the form. My reason was to avoid nagging someone who may be typing an email address they already use. I wanted the login experience to feel less interruptive, rather than showing messages while the person is still entering their details. This difference is a user-experience decision; it does not provide security against user enumeration. Claude helped implement the validation behaviour, and I reviewed and tested the forms. Screenshots 07 and 08 show the difference between the sign-up and login behaviour.

### 3. Why did you use `type="tel"` instead of `type="number"` for the phone field?

I used `type="tel"` because a phone number is an identifier, not a value we need to calculate with. During my test, the number box displayed the leading zero as typed, but the value was treated as a number and became `8031234567` instead of `08031234567`. Pressing the Up arrow changed it again to `8031234568`. This showed me that a number input was not suitable for phone numbers. The text-based `tel` input preserved the leading zero and also allowed international numbers beginning with `+`. My screenshots 09a–09c show the number-input behaviour, while screenshot 10 shows the text input working. Claude also tested additional input problems.

### 4. Pick one of your validation rules. What breaks without it, and which legitimate patient does it wrongly block?

One rule I chose is the password length rule of 8 to 64 characters. Without a minimum length, patients could create very short passwords that are easier to guess. Without a maximum, someone could submit an extremely long password, which could create unnecessary processing work when password hashing is introduced in Task 4. However, the rule can also inconvenience legitimate patients. Someone who prefers a short, memorable password may be blocked by the minimum, while someone who uses a passphrase longer than 64 characters may be blocked by the maximum. I accepted these trade-offs for this assignment. Claude helped document and implement the validation, while I made the decision about the limits.

### 5. What is user enumeration, and where could CarePoint leak it? What would you say on the log-in and reset pages to avoid it?

User enumeration happens when a system reveals whether an email address belongs to an existing account. This is a privacy concern for CarePoint because knowing that someone has an account could suggest that they are a patient of the clinic. An attacker could use this information to target people with scam messages. The login and password-reset responses must therefore avoid confirming whether an email is registered. I would use “Email or password is incorrect” on the login page and “If that email is registered, we have sent a link” on the reset page. The enumeration document also identifies sequential patient IDs as another information leak because they can reveal record counts. These protections still need to be completed as part of Task 4.

### 6. Pick one accessibility problem, explain how it was found and what you changed.

One problem found during the accessibility audit was that booking form errors were displayed as red text only, without an icon. This meant someone who could not easily distinguish colours might not recognise the message as an error. The problem was identified through the audit's review of the form code and its accessibility checks. Claude helped identify and document it as A2. The fix was to add a caution icon alongside the error text, so the message is not communicated through colour alone. Claude made the code changes, and the automated checks were run again afterwards. The after-checks reported no remaining issues in the checks they covered. I understand that automated checks do not replace testing with a real screen reader.

### 7. Which problem did only Narrator find, and what does that tell you about automated checks?

The problem was A6, involving the Date and Time field on the booking form. When I used Windows Narrator in Chrome, it announced the field as five separate spin buttons: day, month, year, hours and minutes. It also announced that the year could go as high as 275760. The automated accessibility checks did not identify this problem. This showed me that automated tools can catch some accessibility issues, but they cannot fully tell me what a person using a screen reader will experience. A hint was added to explain the five parts and how to change them, but the problem is not completely solved. A better solution would be to let patients choose from available appointment slots.

### 8. Why does the sign-up button use `aria-disabled` and not `disabled`? What went wrong with the hidden-button version?

I chose `aria-disabled` because I wanted the Create account button to remain visible and reachable through the keyboard even when the form was not ready. A button with the actual `disabled` attribute leaves the tab order, which can make a keyboard or screen-reader user lose their place. The `aria-disabled` version stays reachable, and pressing it explains what needs attention. I also tried hiding the button until all fields were valid, but rejected that approach. In screenshot 13a, there was no button while the form was incomplete, which could confuse users. Claude deleted that experiment branch at my request. I kept the version shown in screenshot 14, where the button remains visible and explains why it cannot proceed.

### 9. What did your attacks through the form let through, and which of those were your own bugs?

Claude ran 19 attempts against the real sign-up form on my machine, using a throwaway database. The form blocked nine invalid inputs, but allowed others through, including a name containing a script tag, digits-only names, duplicate email addresses and the invalid international number `+0000000000`. The important form bug was that it checked the trimmed name and cleaned phone number but sent the original values to the server. This meant padded names and phone numbers with spaces or hyphens were stored in their original form. Claude fixed this at my request. The follow-up results in evidence 15b showed that the values were now stored in cleaned form. I did not personally run the attack script; Claude did.

### 10. What happened when you sent a request straight to the endpoint?

Claude sent three direct requests to `POST /api/register` using curl, without going through the sign-up form. The server accepted all three and returned `201 Created`. One request contained an invalid name, email, phone number and password; another had an empty body; and the third contained a 200,000-character name. The database also stored those records. This showed that the server was not enforcing the validation rules I had defined for the browser form. The rules were only protecting the normal form experience, not the endpoint itself. The server did not reject any of the three requests. Claude carried out these tests against a throwaway database on my machine at my request. The results show why server-side validation is essential in Task 4.

### 11. Why did you use `git revert` instead of `git reset --hard`, and what went wrong the first time?

I used `git revert` to undo the regretted password change. The commit was still local and had not been pushed, but there were two later commits on top of it. Using `git reset --hard` would have thrown away those later commits as well, so I chose `git revert` to undo only the specific change while preserving the later work. The commit was `b4a7cc6`, which reduced the password maximum from 64 to 6 characters, making it impossible to meet the minimum of 8. My first revert attempt stopped in the Vim commit-message editor, which I closed without saving. I then had to clear the staged changes before trying again with `--no-edit`. The successful revert was `5be57dc`.

### 14. What is the most important thing still open in Task 3, and what will you fix first in Task 4?

The most important open issue is that the registration endpoint has no server-side validation. The direct curl tests showed that it accepted invalid details and even an empty request. This is a serious gap because anyone can bypass the browser form and send a request directly to the server. In Task 4, I would fix this first by adding server-side validation so the endpoint checks the submitted information independently of the browser. I would also address duplicate email registration, secure password hashing and the login and password-reset functionality. Other issues remain, including the terms placeholder and the Date and Time accessibility problem. I would prioritise the security of patient registration first because the current endpoint cannot safely be used with real patient information.
